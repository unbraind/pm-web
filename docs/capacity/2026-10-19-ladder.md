## Duplicate attribution and repair

At 20 subscribers, 50 real mixed HTTP/pinned-CLI updates yielded all 1000 expected receipts plus **140 duplicates**. Traces identify HTTP sequences **0, 4, 5, 8, 9, 14, 23**: each first emits `workspace-changed` from `mutation-events`, then `item-updated` from the route, each writing to all 20 sockets. The 100-subscriber trace repeats the race for sequences **0, 20, 21**, giving 300 duplicates. These are server duplicates; reconnect refresh, peer self-echo and harness counting are not the observed paths.

The one-shot item signal only works when the HTTP announcement wins. The watcher can observe a committed fact while the route still awaits command completion or attribution. The shared delivery sink now records **project + committed item/version** receipts before fan-out. Route announcements read actual committed identities from their pre-dispatch boundary, rather than guessing the latest version; overlapping route/watcher/peer attempts share the receipt. Different versions on one item remain distinct. Peer envelopes carry the identity, and exact-version watcher signals cannot consume another mutation. Receipts cover the existing one-minute replay window and are discarded when the last viewer leaves. Generic identity-free refreshes remain independent.
