# Realtime capacity ladder: 2026-10-19

The ladder stopped at **100 subscribers**: write-to-every-subscriber p99 was **2274.1 ms**, above the 2000 ms SLO. All 5000 expected receipts arrived, with **100 duplicate receipts**. The 1000 and 3000 rungs were not started. This is the first failing rung, not a certified passing capacity: no requested rung passed. Host load remained above four logical CPUs, so this run does **not** certify quiet-host or hosted capacity.

Related investigation: `pm-web-h4vh`; duplicate-receipt follow-up: `pm-web-4f52`; companion: `pm-cli-website-ghe1`. Measured public revision: `8e9cc9713778f9ff945eb28c57d827d20cf75995`; package and pinned pm CLI: `2026.10.19`. Runtime behavior and dependency pins are unchanged.

## Workload and hardware

Linux x64, Intel Core i5-7400 at 3.00 GHz, four logical CPUs, 31.3 GiB RAM; Node v24.19.0, npm 11.17.0, Bun 1.3.5 for release validation. One fresh production server, one temporary synthetic project, 100 distinct authenticated editor identities, five concurrent HTTP API writer lanes and five separate pinned-CLI process lanes, five independent updates per lane (50 total). CLI writes represent shared-directory application writes; actual pm-gpt/MCP processes were not launched. Writers are sequential within each lane and concurrent across lanes: this is a finite closed-loop workload, not a sustained offered rate.

The existing disposable real-Postgres wrapper initialized the test schema. The ordinary 15-second filesystem sweep, shared mutation subscription and LISTEN/NOTIFY policy remained enabled. The initial filesystem baseline completed before writes. Loopback read/write rate limits were 100000/minute. Tracing was disabled. A 4000 ms drain after the final writer settled covered the 2000 ms SLO and retained a window for delayed duplicates. Larger rungs would require fresh prefixes and a newly recorded host snapshot; the failed first rung prohibited advancing.
