The repaired workload passes at **100 and 1000 subscribers**, with **zero loss and zero duplicates**. Commit-to-every-subscriber p99 is **1116.6 ms** and **1928.3 ms**, against the unchanged **2000 ms** SLO. The **3000** rung fails during connection setup, before writes; the ladder stops there. This finite busy-host measurement provides no 3000-subscriber, quiet-host or hosted-capacity certification.

## Duplicate attribution and repair

At 20 subscribers, 50 real mixed HTTP/pinned-CLI updates yielded all 1000 expected receipts plus **140 duplicates**. Traces identify HTTP sequences **0, 4, 5, 8, 9, 14, 23**: each first emits `workspace-changed` from `mutation-events`, then `item-updated` from the route, each writing to all 20 sockets. The 100-subscriber trace repeats the race for sequences **0, 20, 21**, giving 300 duplicates. These are server duplicates; reconnect refresh, peer self-echo and harness counting are not the observed paths.

The one-shot item signal only works when the HTTP announcement wins. The watcher can observe a committed fact while the route still awaits command completion or attribution. The shared delivery sink now records **project + committed item/version** receipts before fan-out. Route announcements read actual committed identities from their pre-dispatch boundary, rather than guessing the latest version; overlapping route/watcher/peer attempts share the receipt. Different versions on one item remain distinct. Peer envelopes carry the identity, and exact-version watcher signals cannot consume another mutation. Receipts cover the existing one-minute replay window and are discarded when the last viewer leaves. Generic identity-free refreshes remain independent.

## Latency attribution and repair

The fresh baseline proves detection delay: CLI append-to-detecting-read p99 is **446.3 ms**, including the 250 ms wait and metadata checks. The follower now wakes on history-directory changes or HTTP/NOTIFY signals, preserving wakes during in-flight reads. Exact metadata checks, the 250 ms fallback and five-second full-read safety admission remain enabled. Fixed 100-subscriber detection p99 is **194.6 ms**. A real separate-process append with a 10000 ms test poll must wake within 2000 ms; reverting the follower to its timer loop fails that assertion.

The original 2274.1 ms event has no trace, so its exact historical cause cannot be reconstructed. In these fresh traces, the **250 ms poll/metadata/SDK path**, rather than the five-second safety scan, sets detection tails. Persistence and SDK read/classification still vary under host pressure. Fan-out already serializes once with no per-subscriber awaits and is not rewritten.
