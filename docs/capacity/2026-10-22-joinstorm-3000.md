# Presence join SQL cost and 3000-subscriber attempts: 2026-10-22

**The 3000-subscriber target remains unmet. No higher measured admission limit is
established.** All 18 unprofiled attempts are retained: the baseline passes 2/9
complete 3000-reader roster/readiness checks; the candidate passes 0/9. The
candidate has 209 failed readiness probes out of 2900, versus 61/3032 before.
Every candidate attempt stops before its final 3000-person roster barrier.

The change reduces SQL work, with behavioral regression proof: shared-principal
initialization uses one statement rather than three, and each fan-out authorization
query is restricted to at most 32 distinct principals. This is useful bounded-work
evidence; it does not establish the requested readiness or capacity target.

The original largest named CPU sample group was PostgreSQL. PostgreSQL plus
membership-Set construction also dominated sampled allocation. The change removes
two of three shared-principal setup round trips and avoids returning the entire
3001-member grant roster per 32-viewer slice. The fresh subset query includes
owner, direct shares and group members; every sink still checks its own principal.
Owner/direct/group joins and committed revocations run against real PostgreSQL in
the new regressions. No authorization cache or invalidation assumption is introduced.

HTTP output callbacks and logging become the largest named CPU sample groups.
Presence was already serialized once per project snapshot: the baseline prepares
22 frames and submits 12,587 event writes; after prepares 39 and submits 20,207.
Scoped fan-out CPU is only 183,264 / 357,693 microseconds, while later transport,
SQL callbacks, logging and scheduler waits appear in broader samples. Full-roster
wire bytes still grow quadratically with population. Removing SQL amplification
alone has not solved admission under this workload.

Raw CPU/heap captures stay external; public aggregates contain relative function/
module sites and no source URLs, principals, tokens, SQL parameters or payloads.
SQL cumulative callback latency overlaps across requests and excludes pool checkout.
Inspector allocation is sampled, includes collected objects and excludes external
Buffer backing memory. CPU sample times include startup and scheduling delays;
they are not exact process CPU microseconds. Different attempts/windows prevent a
controlled percentage claim. The lower allocation counts are measured observations,
while query count/cardinality bounds are independently covered by regressions.

## Design and preserved guarantees

Every admitted subscriber reads owner/direct/group access and display name in one
SQL snapshot, then performs the same per-request resume validation. Fan-out still
refreshes authorization before every yielded slice of at most 32 viewers; only
that slice's distinct principals are supplied to the query. The per-viewer access
check, captured event/registration boundaries, failed-slice cleanup and fresh checks
after transport drain remain in place.

Presence framing, fixed one-second coalescing and the full-roster frontend protocol
are unchanged. Admission/pool limits, 32-viewer socket slices, queue bytes/batches,
stall deadlines, replay retention, cursor epochs/order and deduplication are retained.
See [the protocol](../realtime-fanout.md).
