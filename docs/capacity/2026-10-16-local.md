Stage observations and attribution:

- In T2, CLI pre-append p99/max **2247.5 ms exceeds the entire SLO by itself**. Its observed index-file-lock wait reaches **2071.0 ms**. The detecting SDK read/classification also reaches 1106.7 ms. These are different distributions; their quantiles must not be summed. HTTP pre-append p99 is 465.3 ms. The full write/subscriber-pair p99 is HTTP 661.7 ms versus CLI 2964.9 ms.
- The pinned SDK uses the same exclusive history-event-index file lock for `queryHistoryEventIndex` and `appendHistoryEntryWithEventIndex`. The appender acquires it before the authoritative append; the query also validates stream sizes under the lock. The measured acquisition stall is in the SDK locking path. Shared-lock contention is an inference supported by that implementation; the probe does not separately count failed acquisition attempts or split retry backoff, lock-file I/O and scheduling. The relative contribution of readers versus competing writers also remains unproven.
- The package polling wait stays below 236 ms in these traces. Fan-out already serializes once and synchronously reuses those bytes across the project client set. There are no per-client awaits or per-event authorization queries. SSE connection authorization remains per subscriber; this work changes neither its policy nor its lifecycle. The same event order, replay window and item/version deduplication remain in effect.
- Local HTTP events are delivered before asynchronous `pg_notify`; self-notifications are discarded. Separate CLI writers are found through committed mutation replay. No local measured receipt depends on cross-instance NOTIFY transport, so this experiment cannot attribute cross-instance batching.
- Host load rose after the initial baseline. T2 server CPU p95 was only 26.2% of one core and loop p99 37.9 ms. Those signals do not show an exhausted SSE server; they also do not exclude shared-host CPU/I/O scheduling effects. Tracing perturbs scheduling. The original busy-host breach has no stored stage trace and its exact cause remains unknown.

Probe method: `--trace true` explicitly preloads a test-only module into the owned server and measured CLI children. It observes real file-handle append completion and, only in single-update CLI children, the interval from the first attempted index lock file open until successful lock payload write. This is a **lower bound** on SDK lock acquisition (cleanup-gate waits before the first open are omitted), nested in timestamp-to-append. It includes lock-file open/retry and payload-write scheduling; it does not isolate mutex wait from I/O or scheduling. It is not a second additive stage and does not measure fsync. CLI child scope prevents attributing a concurrent server reader lock to a writer. HTTP lock wait is not measured separately. Source hooks bracket the package replay read, classification, broadcast/shared serialization, and every client write. Exact source-anchor checks fail closed on drift. No dependency files or production artifacts are rewritten on disk. With tracing off no production probes, clocks or allocations execute.

For a read that starts before the append finishes and later observes the fact, polling wait is zero and read/classification starts at append completion; this splits overlapping stages without a negative delay. Direct HTTP events use append-to-route-broadcast instead. Samples through serialization are one per write per origin (25); client stages contain all 2500 receipts per origin. Timings are not acknowledgement-subtracted or zero-clamped. Probe gaps, overflow and negative stage clocks invalidate the run. Final code also emits correlated per-write critical paths, excluding incomplete writes.

Three full traced attempts and two small probe-diagnostic runs were explicitly inconclusive during probe development (missing append observation in the CLI focused bundle, then a misplaced trace-directory creation in the periodic resource sampler). They are excluded from every table. T1 setup overlapped the end of the final inconclusive diagnostic; their write observation windows did not overlap. T2 and T3 ran serially without another task measurement.

The tables measure the last first-receipt for each complete write. History timestamps have millisecond precision and precede final persistence; they are not fsync timestamps. Loss is absence at the end of the finite drain window. CPU refers to one core, RSS is sampled, and the workload is closed loop. This single host, loopback, co-located server/writers/readers, disposable database and small trackers do not prove hosted capacity, sustained throughput, proxy/browser behavior, multi-instance fan-out, slow-reader buffering, large-project costs, reconnect/recovery or new ordering guarantees. The 60-second / 10000-fact replay budgets remain unchanged.
