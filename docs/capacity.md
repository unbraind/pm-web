# Reproduce collaboration capacity

Use a package checkout and the **existing disposable real-Postgres test service** used by `scripts/with-test-db.ts`. The harness never provisions a database service. Do not point it at a live deployment or a database containing real projects. It seeds unique synthetic rows in the selected test database and deletes only those rows after stopping its server. Project directories and child configuration homes are temporary. No hosted URL or existing project directory is accepted.

Install dependencies with `npm ci --ignore-scripts`. Pick an external output prefix in `CAPACITY_OUTPUT`; the two files must not exist. The normal test wrapper supplies the same `DATABASE_URL`, schema initialization and disposable database preflight used by the integration suite. For another isolated test service, export `DATABASE_URL` first.

```sh
node scripts/with-test-db.ts node scripts/capacity.ts --rungs 100,1000,3000 --writers 10 --writes-per-writer 5 --slo-ms 2000 --drain-ms 4000 --output "$CAPACITY_OUTPUT"
```

The command builds with `npm run build`, then starts `node dist/server.js` with a test-only telemetry preload. It never executes `prepare`. With no `--output`, reports go to a newly allocated system temporary directory. Existing reports are never overwritten. Success exits zero; loss, SLO breach, write/disconnection/health failure, or an incomplete experiment exits nonzero and stops the ladder. Startup/measurement failures produce an explicitly inconclusive report.

`--rungs` must increase and stay at or below **3000**. `--writers` is 2–32 and `--writes-per-writer` is 1–100. Half the lanes use signed sessions against the real authenticated HTTP API; the remaining lanes run the repo-pinned pm CLI as separate processes, representing shared-directory writes by other applications. An odd writer count gives CLI the extra lane. Every lane writes sequentially, and all lanes run concurrently. This is a closed-loop workload; the report records duration and exact write count, not an offered fixed request rate.

Every rung uses one fresh project, one fresh production server, a unique authenticated editor identity per subscriber, and separate pre-created items for every measured mutation. The production mutation subscription, LISTEN/NOTIFY bus and 15-second filesystem sweep stay enabled with their ordinary cadences. Writes wait for the first filesystem baseline, which also allows the primary mutation subscription to attach. Since all sockets share loopback, only read/write rate-limit tiers use the integration harness's 100000/minute setting. Child environments use temporary homes and omit ambient OIDC, graph, telemetry, provider and project configuration.

The SSE parser follows actual network streams. Only `item-updated` and item-specific `workspace-changed` events count as delivery; presence, graph events and generic invalidations cannot conceal loss. Unique measured item IDs identify writes even if events arrive before the writer's acknowledgement. Duplicate counters include every subsequent matching mutation event, including duplicates from a second delivery path. Memory used for receipt accounting is bounded by subscriber and write counts; raw frames and production logs are drained rather than retained.

Each write has exactly one update. After the observation window the harness reads its **authoritative history entry timestamp**, verifies that the update committed, and computes first-receipt latency for every subscriber. That timestamp has millisecond precision and is assigned during the mutation before final persistence, so latency conservatively includes that persistence interval; it is not a filesystem fsync timestamp. Receipt times use the load generator's high-resolution wall clock on the same host. No response-time subtraction or zero clamping hides pre-acknowledgement deliveries. Negative clock deltas invalidate the experiment.

The primary table computes one latency per complete write: its last first-receipt across **all** subscribers. Nearest-rank p50/p95/p99/max are reported. The ladder stops when this p99 exceeds `--slo-ms` (default 2000), or if any committed mutation is absent at any subscriber. JSON also includes all write/subscriber-pair and per-transport distributions, each subscriber's missing sequence numbers and duplicate count, disconnected clients, committed and failed writes, and both `/healthz` counter snapshots. Missing writes never become successful quantile samples. A nonzero duplicate count is evidence to investigate; it is reported separately from loss.

`--drain-ms` (default 4000) must cover the SLO. It is the observation window **after the final writer settles**, retained even if all expected events arrived, to observe delayed duplicates. Loss means absent at the end of this finite window, not a proof of permanent loss. No automatic reconnect masks disconnections. The harness cleans up every connected stream, joins its child, then deletes only its uniquely owned rows and temporary directories. Unexpected process termination can leave synthetic rows or temporary files; never clean them by broad database or filesystem deletion.

The preload samples server RSS and CPU every 250 ms and tracks event-loop delay with a 10 ms histogram, reset before writes. CPU is percent of **one core**; the report retains p50/p95/p99/max of interval CPU and peak sampled RSS. It also reports load-generator CPU/event-loop delay, host CPU count/model/RAM and initial load. A separate connection samples only aggregate counts from `pg_stat_activity` in the selected test database every 500 ms: server connections (including its LISTEN connection), total test-database connections and the cluster's configured maximum. No other session SQL or identifiers enter the report. The observer and any concurrent integration tests are included in the database total.

First-limit attribution is an observation, not a causal proof: near-exhausted PostgreSQL connections, server event-loop delay, single-core CPU pressure, load-generator scheduling or low free host memory. Without such a signal a failed rung explicitly says the resource is unidentified. Passing every requested rung means **no tested limit observed**, not an unlimited capacity claim. Consult the complete JSON when interpreting a stopped rung.

The initial mixed-writer measurement exposed committed CLI facts missing from SSE even though they remained readable in the SDK event index. An exclusive timestamp cursor skips a fact when it becomes visible after a later timestamp has advanced that cursor. The production follower now re-reads an inclusive **60-second** window, pages through all its facts, and deduplicates by item/version. State survives read-error restarts. This is bounded to **10000 facts per active project**; overflow raises an observable mutation watcher error instead of silently evicting live receipts. The ordinary filesystem refresh remains a safety net. Mutations that become visible more than a minute after their timestamp and rates beyond the window budget are limits requiring a monotonic visibility cursor upstream. A deterministic real-CLI regression publishes a fact behind an already-advanced cursor, verifies the SDK's exclusive tail misses it, and requires overlap to deliver it once. No SDK is mocked and no existing history entry is rewritten.

The release gate includes `test/capacity.acceptance.ts`: 20 real subscriber sessions and five concurrent lanes (two HTTP, three CLI), one update each, zero loss/duplicates, and **every** delivery within two seconds. It is a separate `accept:capacity` step, following the existing packed-acceptance pattern: the production baseline alone takes 15 seconds, and a focused test process took 32 seconds on the busy host (live scenario 29.5 seconds). It is therefore outside the normal test glob's parallel fanout. Ordinary receipt-accounting and cursor regressions remain in the normal suite. Run the real-process smoke alone with:

```sh
npm run accept:capacity
```

For an isolated copy of the hosted code and test database, use the first command with `DATABASE_URL` set to that disposable copy, retaining the output files externally. No production configuration or live endpoints are read. This exercises the same shared-directory write mechanism, rather than launching pm-gpt or MCP. It does not establish sustained throughput, browser/proxy behavior, slow-consumer buffer bounds, multi-instance fanout, reconnect replay, or large-project performance. The bus is enabled but single-instance local events do not traverse a second server.
